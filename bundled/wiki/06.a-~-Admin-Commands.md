### init

_Command:_ `mcdev init`

_Alias:_ -

Creates the basic configuration file `.mcdevrc.json` and `.mcdev-auth.json` in your project directory. You may add more credentials by re-running the same command again, e.g. to add production and sandbox credentials next to each other.

In addition, it initializes an npm package for you, installs recommended npm dependencies and places our default IDE configuration files for ESLint, Prettier, Git and VSCode into your project directory.

**Starting with v10:** the CLI and generated tooling require Node `^22.22.2 || >=24.15.0`, including the editor's ESLint runtime. New projects receive runtime-scoped SFMC/Unicorn/JSDoc linting, separate Prettier with `prettier-plugin-sfmc`, and `.prettierignore` protecting generated/temporary paths and migration `.BAK` files. Generated scripts are `lint` (`eslint .`), `lint:fix` (`eslint . --fix`), `format` (`prettier . --write`) and `format:check` (`prettier . --check`); run lint and formatting checks separately. These are not changes to mcdev's own contributor scripts. See the [v10 migration guide](/Accenture/sfmc-devtools/wiki/03.a-~-Migrating-to-v10) for exact commands, execution scopes, editor setup and upgrade safeguards.

The initialization ends with the creation of your Git repository and the first backup of your SFMC instance when Git is available. Newly initialized repositories use `main`; existing repositories keep their branch names. Starting with mcdev 10.1.1, the optional initial push uses the current branch (`git push -u origin HEAD`). This released fix does not establish that the pending extension or other local Git annotations below have shipped.

> **Pending release (local, unreleased implementation):** during fresh `init`, unavailable Git triggers a warning and skips Git initialization, remotes, staging, commits and pushes while non-Git setup continues. `--y.gitRemoteUrl` and `--y.gitPush` do not override this skip. Other Git failures follow command-specific handling; not all abort setup or produce a nonzero exit. `upgrade` does not run Git setup or issue an unavailable-Git warning.

In this pending implementation, recursive configuration repair and initial retrieval use the active Node interpreter and mcdev package, including a selected extension bundle; another `mcdev` on PATH is not required. Child command failures are not propagated by this helper. Tooling dependency defaults and the canonical formatter plugin resolve from the active mcdev package. Node/npm must still be on PATH for project tooling. See the [extension README](https://github.com/Accenture/sfmc-devtools-vscode/blob/main/README.md) for runtime and CLI-source settings.

_Example - initialize project / add additional credentials:_

```bash
mcdev init
```

_Example - update credentials:_

```bash
mcdev init yourCredentialName
```

The interactive setup will ask you for an `EID (Parent MID)`, `Client ID` and `Client Secret` of an installed package. It also asks for the `Authentication Base Uri`. Each installed package on a given SFMC instance shares the same tenant sub-domain and always shows you 3 domains (Auth, REST and SOAP).

Example URL: `https://mcg123abcysykllg-0321cbs8bbt64.auth.marketingcloudapis.com`

> **Note to CLI experts:**
>
> Prefer the interactive local `mcdev init` wizard for credential entry. Do not send secrets through chat or paste secret-bearing commands or raw logs: command-line values can enter shell history, and mcdev records its arguments in the normal debug logfile.
>
> For controlled unattended setup, `--skipInteraction` (aliases `--yes`, `-y`) accepts the dotted `--y.*` answers listed below. Credential setup requires all of `credentialName`, `client_id`, `client_secret`, `auth_url` and `account_id`; the flag alone does not supply them. An omitted or invalid `developmentBu` leaves a `???` source-market mapping requiring manual correction. This mode also bypasses ordinary Yes-default configuration-file override prompts. Historical version-gated replacements bypass those prompts regardless of the flag; package scripts and dependency updates have no separate approval prompt. Review project customizations and backups first.
>
> With Git installed, fresh `init` runs Git setup and identity handling; `upgrade` only refreshes project configuration/tooling and does not run Git setup or identity handling. Confirm the intended Git-resolved `user.name` and `user.email` beforehand and configure them repo-locally if needed. `--yes` reuses existing identity; there are no name/email `--y.*` answers in this implementation, and missing identity must be resolved before relying on unattended commits.
>
> This is not a universal no-prompt mode: cloud-synchronized/user-profile path warnings can still require confirmation. Other commands may still ask when selectors are omitted, `createDeltaPkg` lacks a range, or combined `build` lacks an explicit `--purge`/`--no-purge` choice. Supply valid command-specific inputs rather than assuming `--yes` covers them.

| CLI Argument         | Description                              |
| :-------------------- | :---------------------------------------- |
| `--y.credentialName` | Credential name of your Business Unit    |
| `--y.client_id`      | Salesforce Marketing Cloud client ID     |
| `--y.client_secret`  | Salesforce Marketing Cloud client secret |
| `--y.auth_url`       | Marketing cloud auth url                 |
| `--y.gitRemoteUrl`   | URL of your git remote repo              |
| `--y.account_id`     | MID of the parent BU                     |
| `--y.downloadBUs`    | Download all the BUs: `true` or `false`  |
| `--y.gitPush`        | Do the first git push: `true` or `false`; `true` still requires an `origin` push URL and a successful fetch finding no remote branches |
| `--y.developmentBu`  | set the name of your development BU      |

### join

_Command:_ `mcdev join`

_Alias:_ -

This command clones an existing Accenture SFMC DevTools project from a Git repository and sets up your local environment. It then creates the basic credentials file `.mcdev-auth.json` in your project directory and installs the recommended npm dependencies, including Prettier with `prettier-plugin-sfmc`.
Git is required for cloning. In the pending local implementation described under [init](#init), unavailable Git causes an actionable error and a nonzero CLI exit before the join questions; it does not take the optional warning-and-skip path.

One could use `mcdev init` instead, but this command combines cloning and setup. Starting with v10, the same runtime requirements and generated-tooling safeguards apply as for [init](#init) and [upgrade](#upgrade); review existing project configuration and resolve any reported incomplete migration before relying on the new tooling.

_Example:_

```bash
mcdev join
```

### upgrade

_Command:_ `mcdev upgrade`

_Alias:_ `mcdev up`

In the current local, unreleased implementation, `upgrade` does not require Git, initialize a repository or issue an unavailable-Git warning. It refreshes project configuration/tooling, not the running CLI or extension bundle. Update the extension or deliberately select a compatible CLI when its bundled version is older than the project.

This upgrades older Accenture SFMC DevTools projects to the newest standard: outdated configuration files are refreshed, the recommended npm dependencies are installed, and the current IDE configuration files are copied into your project folder. See [init](#init) for more details.

**Starting with v10:** `upgrade` processes the ESLint/Prettier configuration and `.prettierignore` one file at a time, then updates scripts and dependencies. It removes direct `eslint-config-ssjs` and `eslint-plugin-prettier` declarations from both dependency sections; pre-v10 migration also retires `prettier-plugin-sql`. `eslint-check` is removed without an alias: use `npm run lint` for diagnostics, `npm run lint:fix` for lint fixes and `npm run format` for formatting. Run `npm run format:check` separately for the formatting CI gate. Unrelated dependencies are preserved.

The generated `.prettierrc` uses `prettier-plugin-sfmc`, standard SFMC base options and only the `.mcdev-validations.js` override for `trailingComma`; separate SQL and SSJS overrides are unnecessary. A legacy `.beautyamp.json` is preserved as `.beautyamp.json.BAK`. Review existing configuration and editor settings before approving replacement, and reapply wanted customizations. Tooling defaults are derived from the installed mcdev package's manifest. Only equal/newer simple versions in `devDependencies`, optionally prefixed with `^` or `~`, are preserved; missing, older or non-simple specifications are installed at the default version. A declaration in `dependencies` alone does not satisfy this check. `sfmc-boilerplate` is not a generated tooling dependency, although existing declarations are not automatically removed. The project is set to `type: "module"`; missing, invalid or broader `engines.node` ranges are replaced with mcdev's supported range, while valid subsets are preserved.

Configuration files are processed and written sequentially, without a coupled preflight. Missing files are created and identical files are reported as needing no update. Ordinary differing files receive an optional Yes-default override prompt; declining skips only that file and does not fail the upgrade. Historical version-gated `forcedUpdates` replacements and `--skipInteraction` bypass the prompt. Managed `lint`, `lint:fix`, `format` and `format:check` scripts are replaced with the defaults without a separate approval prompt; only exact legacy boilerplate commands are retired, preserving custom or chained legacy commands.

When a file is replaced or retired, it is renamed to `.BAK`; if that backup already exists, it is replaced with the latest pre-upgrade file. Repeated upgrades therefore continue and refresh the backup. File inspection/read/rename errors are not silently ignored. Earlier changes are not rolled back, and other files may already have been processed. The npm phase only runs after the file phase succeeds, and the upgraded project version is saved only after npm succeeds. Start from a clean committed state and review the diff; `.BAK` files are a convenience, not rollback protection. If npm installation fails, repair the installation and rerun `mcdev upgrade`. A retry does not guarantee installed-tree or lockfile reconciliation: dependency checks use `package.json` declarations, not install artifacts. If declarations already match and no retired dependencies remain, npm can be skipped even when the lockfile or installed packages are missing. See the [v10 migration guide](/Accenture/sfmc-devtools/wiki/03.a-~-Migrating-to-v10) for runtime/editor scopes, recovery and verification.

_Example:_

```bash
mcdev upgrade
```

### migrate

_Command:_ `mcdev migrate [cred/bu|cred/*]`

_Alias:_ -

**v10:** local asset-file migration under `directories.retrieve`, either for one resolved credential/BU (`cred/bu`) or for every BU of one credential in a single run (`cred/*`). It does not migrate deploy/template trees. Run `mcdev upgrade` first when required by the project-version guard, review and commit that separately; configuration defaults and file migration are different steps.

The command resolves the argument to one configured credential/BU and reads each owning JSON's `assetType.name` to choose the current group, so a historical group that holds several asset types is split correctly. Omit the argument for interactive credential/BU selection. Only exact `cred/*` for a configured credential expands to all its BUs. Other unresolved selectors, including bare `*` and `unknownCredential/*`, use the existing interactive credential/BU selection; with `--skipInteraction`, mcdev logs an error instead. Selectors with extra slash components or empty components, such as `cred/bu/extra`, `cred/` or `/bu`, are rejected without selection. Only the resolved BU's retrieve tree is touched, and the reported result is `X moved, Y conflicts, Z skipped`. Before moving anything it states that only the local retrieve folder is reorganized with no changes on the server; each historical group shows its own progress bar, and asset types without a current mapping are left in place and reported with a count instead of being skipped silently. With `cred/*`, mcdev reports the results per BU with every output line prefixed `credential/BU`, isolates each BU so a conflict in one BU does not stop the remaining BUs from being migrated, and closes with a summary `processed N BUs of <cred>, M of them had conflicts`. There is deliberately no bare `*` form; `cred/bu` remains the safer choice when you want to review each BU separately.

Moves preserve file bytes/modes and keys. If any destination path already exists — even with identical content — the whole asset stays in place and is reported as a conflict, so no asset is moved partially; resolve the conflicts and re-run. Only empty directories are removed: after a group is migrated, empty folders under its retired group root are cleared bottom-up, including ones that were already empty before the run. A surviving folder is reported either as now-empty and manually removable (the operating system refused the delete) or as still containing files, which must **NOT** be deleted and is listed with its remaining entries. Directories containing links or other special entries are classified as nonempty, just like directories containing files; those entries are not reported as separate leftover paths. There is no rollback and multi-file migration is **not crash-atomic**, so start from a clean committed snapshot and review the result. No authentication, server calls, configuration/package updates, branch switches or automatic commits occur.

**Downmerge configuration once, then migrate each branch's own assets.** Pause work and promotions, including on existing release, feature and hotfix branches, and record each branch's clean starting commit and pending edits/additions/deletions. Run `mcdev upgrade` on the topmost branch (for example `prod`), commit only the tooling/configuration changes and downmerge them. Then run `mcdev migrate cred/*` separately on each branch from `prod` down to `dev`, repeating for other credentials. Review conflicts and skipped assets, and commit each branch's mechanical moves separately from content edits. Do not downmerge one branch's asset migration as a substitute for migrating the others, promote pending work or copy/retrieve another branch's content to equalize versions. Rehearse merges and delta packages before resuming work; a clean merge still needs content/layout checks. See [Migrate assets on every branch](/Accenture/sfmc-devtools/wiki/03.a-~-Migrating-to-v10#migrate-assets-on-every-branch) for the full checklist.

### document

_Command:_ `mcdev document <business unit> <TYPE>`

_Alias:_ `mcdev doc`

Creates human-readable documentation for your metadata. This command is executed by default for supported types unless you changed your config manually (`metaDataTypes.documentOnRetrieve`). Therefore, running it manually is typically not required. You can choose to generate **HTML** (`html`) or **Markdown** (`md`) docs via `options.documentType`.

The default format is set to `md` as Markdown renders nicely in Git as well as in VSCode's Markdown preview and can be copied from there into Confluence and other applications without losing the formatting.

As standard roles are often not used by projects, we have the optional setting `options.documentStandardRoles` which is by default set to false

**Currently supported types:**

| Name           | CLI Argument    |
| :-------------- | :--------------- |
| Automation     | `automation`    |
| Data Extension | `dataExtension` |
| Role           | `role`          |
| User           | `user`          |

_Example:_

```bash
mcdev document myServer role
```

### describeSoap

_Alias:_ `mcdev describe`, `mcdev soap`

This is mainly aimed at contributors to get a quick overview on available fields for the various [SOAP Web Service API Objects](https://developer.salesforce.com/docs/marketing/marketing-cloud/guide/soap_web_service_objects.html). Optional **`--bu`** selects which Business Unit context to use (defaults follow the tool’s parent-BU behavior). **`--json`** prints the same field list as JSON instead of a text table.
