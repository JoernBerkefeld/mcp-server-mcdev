## Installing a specific version

To work with our **developer-version** or to install a **specific older version** you can select any branch or tag from our git repository during install to do so:

**Most recent developer version (using the GitHub repo & branch name):**

```bash
npm install -g accenture/sfmc-devtools#develop
```

_Note: Regardless of which tag or branch you install_

**Install specific version (using a version tag on npm):**

```bash
npm install -g mcdev@9.0.3
```

**Warning**: When you used the above method to install Accenture SFMC DevTools for a specific version or tag, trying to [update Accenture SFMC DevTools](/Accenture/sfmc-devtools/wiki/3.-Updating-mcdev) might not download the most recently published official version but instead stay on the version or branch you previously selected (in the above examples: develop, 9.0.3)!

> **Note**: The version is currently _not_ updated on the developer branch until a new release is published. Hence, you will not see a change if you run `mcdev --version`.

## Diagnosing a failed command

Start with the normal `logs/<timestamp>.log` for the relevant invocation. Correlate its timestamp, command and credential/BU with the operation that failed; do not simply select the newest file. A multi-BU run may involve several related logs. The normal logfile already records debug-level messages, so `--debug` is not required to obtain them; that flag also enables developer and edge-case features. The optional `*-errors.log` companion contains only errors and is not a replacement for the normal log.

If those details are insufficient, consider the same explicitly scoped command with `--api log` (or `--api=log`). For example, after reviewing the effects and approving any repeated overwrite:

```bash
mcdev retrieve MyProject/DEV query myQuery --api log
```

This executes the operation again and adds API request/response details to the new normal logfile; it does not enrich an existing log. Reconcile partial results first and obtain approval for repeated local overwrites or remote side effects before rerunning a command, especially deploy, delete, execute, init or upgrade. Inspect the logs correlated with that new invocation afterward. `--noLogFile` disables file logging, including the optional error companion, so it cannot be combined with this file-based diagnostic workflow.

Treat logs as sensitive: normal logs include command-line arguments, and API bodies can contain credentials, tokens or account data despite limited token masking. Review them privately and share only the minimal, vetted diagnostic excerpts; do not paste whole raw logs or provide `.mcdev-auth.json`.

## Re-retrieving assets with conflicting local JSON

If a local asset metadata JSON file contains Git merge-conflict markers or otherwise cannot be read as JSON, retrieving that asset by key can replace it with the version from Marketing Cloud. You do not need to retrieve every asset or repair the JSON first.

For readable asset metadata, mcdev uses the previous JSON to identify associated code and binary files for cleanup. If that JSON cannot be read, mcdev skips this cleanup rather than guessing which files to remove. The retrieve replaces the metadata and writes the downloaded files, but obsolete associated files may remain and need manual review. Unrelated files are left alone.

Retrieving replaces local content, so preserve any local edits you want to keep before using it to resolve a conflict. This behavior does not make conflict-marked JSON valid input for deployment or template building.

## Authentication session cache

mcdev stores reusable authentication sessions in a user-level `sessions.json`, separately from the project's `.mcdev-auth.json` installed-package credentials:

- **Windows:** `%APPDATA%\mcdev-nodejs\Config\sessions.json`. If `APPDATA` is unset, the base is `AppData\Roaming` below `USERPROFILE` (or the home directory).
- **macOS:** `~/Library/Preferences/mcdev-nodejs/sessions.json`.
- **Linux and other platforms:** `$XDG_CONFIG_HOME/mcdev-nodejs/sessions.json`, falling back to `~/.config/mcdev-nodejs/sessions.json` when `XDG_CONFIG_HOME` is unset.

Treat this cache as sensitive authentication data; do not commit or share it. A missing file, malformed JSON or a top-level value other than a JSON object is treated as an empty cache. mcdev can authenticate again from the project credentials; the next successful session write replaces the invalid content. This recovery does not repair or replace `.mcdev-auth.json`.

The store rejects symbolic links (including Windows junctions/link reparse points) at the session-file location, and checks existing parent directories for links and unexpected filesystem objects before writing. A link or permission failure is not the same as malformed JSON recovery: use a regular file and real directories with appropriate access rather than redirecting the cache through links.

Writes replace the cache via a temporary file in the same directory; on non-Windows systems the managed store directory and file use owner-only permissions. If persisting a refreshed session fails, mcdev logs `Could not persist refreshed auth session` at debug level and retains that refreshed session in memory for the current authentication service. It can therefore remain usable in the current process, but later processes cannot rely on that refresh having been saved. Check the cache path, permissions and links if sessions are repeatedly missing between runs.

## Using custom CLIs

Some users of Accenture SFMC DevTools prefer to use git bash or other CLIs instead of the operating system's default. Please note that some of the functionality of Accenture SFMC DevTools but also other tools like the Node package manager (npm) do not necessarily function properly in these.

If you encounter problems, we strongly recommend first trying it in the default CLI.

## Missing write access to...on MacOS

Depending on your setup, the default global installs & updates might error out with "Missing write access to /usr/local/lib/node_modules". In this case, prefix your command with `sudo`:

```bash
sudo npm install -g mcdev
```

```bash
sudo npm update -g mcdev
```

![Mac sudo](img/README.md/troubleshoot-mac-sudo.png)

## ...running scripts is disabled on this system

If you see the below error then your system's security settings are rather strict.

![Execution Policy](img/README.md/troubleshoot-execution_policy.jpg)

Steps to solve this:

1. Start Windows PowerShell with the "Run as Administrator" option.
2. Input the following and then hit ENTER: `set-executionpolicy remotesigned`
3. Either you are done now - or you will be prompted with a question to confirm the change (screenshot below). Please type `y` (="yes") and confirm with `Enter`.

![Execution Policy](img/README.md/troubleshoot-execution_policy-2.png)

Please note that this change is global and not just for your current folder.

Alternatively, switching from PowerShell to **Command Prompt (`cmd`)** can resolve script-policy errors in some cases without changing PowerShell's execution policy. In VS Code, run **Terminal: Select Default Profile** from the Command Palette, choose **Command Prompt**, then open a new terminal and retry the command.

## Operation not permitted OR No such file or directory

If you encounter out of the 3 following errors you will have to completely remove Node.JS and install it again afterwards.

**Error 1:** Cannot find module index.js

![index.js not found](img/README.md/troubleshoot-nodejs-index.jpg)

**Error 2:** Operation not permitted

![operation not permitted](img/README.md/troubleshoot-nodejs-permission.jpg)

**How to completely remove Node.js from Windows:**

1. Run npm cache clean --force

2. Uninstall it via the system's `Add or remove programs` (find it by searching in the start menu).

3. Reboot your computer.

4. Look for these folders and remove them (and their contents) if any still exist. Depending on the version you installed, UAC settings, and CPU architecture, these may or may not exist:

    - C:\Program Files (x86)\Nodejs
    - C:\Program Files\Nodejs
    - C:\Users\\{User}\AppData\Roaming\npm
        - (or %appdata%\npm)
    - C:\Users\\{User}\AppData\Roaming\npm-cache
        - (or %appdata%\npm-cache)
    - C:\Users\\{User}\.npmrc (and possibly check for that without the . prefix too)
    - C:\Users\\{User}\npmrc
    - C:\Users\\{User}\AppData\Local\Temp\npm-\*

5. Check your %PATH% environment variable to ensure no references to Nodejs or npm exist.

6. If it's still not uninstalled, type `where node` at the command prompt and you'll see where it resides -- delete that (and probably the parent directory) too.

7. Reboot again!

**Re-install Node.js and Accenture SFMC DevTools:**

Now, please follow the guides above in the [Pre-requisites](/Accenture/sfmc-devtools/wiki/2.-Getting-Started#pre-requisites) section to Install Node.js again and afterwards try again to [install Accenture SFMC DevTools](/Accenture/sfmc-devtools/wiki/2.-Getting-Started#install-accenture-sfmc-devtools).
