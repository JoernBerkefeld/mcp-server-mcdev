While you can use mcdev completely without Git and any task automation, it is strongly encouraged to use both in your daily flow. For these situations, we build a wrapper around the above methods to execute everything except `deploy` with a single command:

### createDeltaPkg


_Command:_ `mcdev createDeltaPkg [commitrange] [--filter] [--range] [--commitHistory] [--dependencies] [--retrieve] [--skipValidation] [--purge] [--no-purge] [--fix] [--shareAsset]`

_Alias:_ `mcdev cdp`

**Prerequisite:** Git-backed delta generation requires an available Git executable and a usable repository with the comparison refs.

> **Pending release (local, unreleased implementation):** the Git-backed delta phase rejects unavailable Git with an actionable error and a nonzero CLI exit before its interactive questions, deploy-folder purge or package output writes. Project configuration is loaded before this delta-phase check. Ordinary retrieve/deploy operations do not require Git.

A programmatic `diffArr` array without an explicit filter bypasses Git comparison. With an explicit filter, `diffArr` is ignored and Git copy mode is used instead. The bypass does not waive caller responsibility or purge behavior; see **Programmatic explicit lists** below.

Prefer `--range` (aliases: `--branch`, `--commit`, `-R`) to supply a branch name, a single commit, or a full range such as `main..HEAD`. The first positional argument is still supported but deprecated and emits a warning. Use your project's actual integration/production branch names in these examples; existing branches do not need to be renamed.

This command is rather versatile and hence can be used in multiple ways. The most potent option presents itself when you configure `options.deployment.sourceTargetMapping` to point to a source `marketList` (usually for DEV-BU with a DEV market) and a target `marketList` (e.g. to a QA BU-market combo and a Production BU-market combo). Given this is configured, it can create all deployable files using Accenture SFMC DevTools's templating engine on the fly for you.

The **minimum configuration** you need to have in your config could look something like the following:

> Note: the following example does not show all necessary parts of the config, just those that are needed for createDeltaPkg.
>
> The example tells createDeltaPkg that the source BU is called `MyProject/DEV` and that there are two targets for deployment, `MyProject/QA` and `MyProject/PROD`. Furthermore, it associates the markets `dev`, `qa`, and `prod` to these BUs to ensure templating is applied - however, the markets in this example are empty, which means no actual string replacement will occur. This is normal for most basic cases in which you would expect 1:1 copies on DEV, QA, and PROD.
>
> When MC Connect is used, one would expect to see the External Keys of the Synchronized DataExtensions be mentioned in the markets for easy auto-replacement.

```json
{
  "credentials": {
    "MyProject": {
      "businessUnits": {
        "DEV": "1235",
        "QA": "1236",
        "PROD": "1237"
      }
    }
  },
  "options": {
    "deployment": {
      "commitHistory": 10,
      "sourceTargetMapping": {
        "deployment-source": "deployment-target"
      }

  "directories": {
    "deltaPackage": "docs/deltaPackage/",
    "deploy": "deploy/",
    "retrieve": "retrieve/",

    "templateBuilds": ["retrieve/", "deploy/"]
  },
  "markets": {
    "dev": {},
    "qa": {},
    "prod": {}
  },
  "marketList": {
    "deployment-source": {
      "description": "Define one 1:1 BU-Market combo here to as source for automated creation of deployment packages; you can create more than one source market list",
      "MyProject/DEV": "dev"
    },
    "deployment-target": {
      "description": "Define n BU-Market combo here to as target for automated creation of deployment packages; you can create more than one target market list and they can be as complex as you like",

      "MyProject/PROD": "prod"
    }

```

**Branch-based Source-Target Mapping:**

For more complex CI/CD workflows where different branches deploy to different environments, you can use `branchSourceTargetMapping`. This allows you to define different source-target mappings per supplied comparison range (often a target branch name):

```json
{
  "options": {
    "deployment": {
      "sourceTargetMapping": {
        "deployment-source": "deployment-target"
      },
      "branchSourceTargetMapping": {
        "sit": {
          "deployment-sit-source": "deployment-sit-target"
        },
        "uat": {
          "deployment-uat-source": "deployment-uat-target"
        },
        "prod": {
          "deployment-prod-source": "deployment-prod-target"
        }
      }
    }
  }
}
```

When `createDeltaPkg` runs, it looks up the **exact supplied range string** in `branchSourceTargetMapping`, not the checked-out branch name. A matching entry replaces the fallback `sourceTargetMapping`. For example, on `uat`, `mcdev createDeltaPkg --range prod` selects the `prod` entry. Writing `prod..HEAD` instead needs that exact key or uses the fallback, even though bare `prod` resolves to `prod..HEAD` for Git comparison.

Without `--filter`, the selected source market list determines the source BU. That **same source BU path is compared across both Git endpoints**; the target market list controls templated output, not a second BU folder to diff. For a source `cred/uat` and target `cred/prod`, compare `prod:retrieve/cred/uat/**` with `uat:retrieve/cred/uat/**` while checked out on `uat`, then template UAT source content for PROD.

**v10 migration preparation:** pause work and promotions and record clean baseline commits, comparison refs and pending edits/additions/deletions on every participating branch. Run `mcdev upgrade` once on the topmost branch (for example `prod`), commit the tooling/configuration changes and downmerge them through the normal chain (`prod → uat → qa → sit → dev`). Then migrate each branch's own assets separately, from production down to development, using `mcdev migrate cred/*` for each credential and committing mechanical moves separately from content edits. Include existing release, feature and hotfix branches; do not use a shared asset-migration downmerge as a substitute for their local migrations. Do not copy/retrieve another branch's content or advance pending promotions merely to equalize content. Rehearse merges and packages and verify that pending work is unchanged before unfreezing. The [full v10 guide](/Accenture/sfmc-devtools/wiki/03.a-~-Migrating-to-v10#migrate-assets-on-every-branch) gives the branch schedule and checks; the [BU comparison details](/Accenture/sfmc-devtools/wiki/03.a-~-Migrating-to-v10#understand-which-bu-is-compared) explain same-source-BU comparisons.

**v10 Git-derived safeguards (normal two-dot and bare-base comparisons):** equivalent byte-identical layout moves are suppressed, including delete/add pairs spanning migration commits, without hiding real pending changes. Migration pairing happens before path filters, which then scope the resulting changes. For each change the adapter compares the committed blobs at both endpoints of the range; when they are byte-identical, both the old and the new path are dropped, so a pure regrouping move produces neither an addition nor a deletion. A moved asset that was also edited stays actionable in its new location, and for a non-rename pairing only the old path is dropped so the asset is not falsely reported as deleted. A deleted extracted companion selects its surviving current-layout owner for an update, rather than an asset deletion; genuinely deleted assets remain deletions. Old merge bases and saved refs may still need temporary compatibility. See the guide before relying on these safeguards.

**Programmatic explicit lists:** when `createDeltaPkg` receives a `diffArr` array without an explicit filter, it uses the caller-managed records without Git comparison or normalization. Downstream action/name and metadata-type filtering still applies. Because Git is not consulted, it also does not apply the migration suppression described above. Mapping lookup still uses the original supplied range string with `sourceTargetMapping` as fallback; that string need not be a valid Git ref for an explicit list. Ordinary template discovery is retained, so the caller is responsible for correct BU/type/key scoping, actions and current source files. An empty array (`[]`) skips per-mapping builds and creates no package output. With explicit purge enabled and multiple source-target mappings, however, deploy folders are purged up front before empty deltas are skipped; do not treat an empty list as a universal no-cleanup guarantee. With an explicit filter, `diffArr` is ignored as before: copy mode uses Git comparison and its safeguards instead.

**Metadata Types for createDeltaPkg:**

Use `metaDataTypes.createDeltaPkg` as an explicit inclusion list for templated delta builds and generated delete instructions. An empty array includes no types in those paths; there is no fallback to `metaDataTypes.retrieve`. Omitting the setting can fail configuration validation. Generated defaults are populated separately from the types marked `typeCdpByDefault`. This list is not the selector for `--filter` copy mode:

```json
{
  "metaDataTypes": {
    "retrieve": ["automation", "query", "dataExtension"],
    "createDeltaPkg": ["automation", "query"]
  }
}
```

**createDeltaPkg with --dependencies:**

You can include dependencies of changed items in the delta package using the `--dependencies` flag:

```bash
mcdev createDeltaPkg --range main --dependencies
mcdev cdp --range main -D
```

In the legacy build path, this analyzes dependencies of changed items and includes them in the package.

**createDeltaPkg with --commitHistory:**

The config value `options.deployment.commitHistory` controls how many past commits are offered in interactive mode. You can override that for a single run with `--commitHistory <number>`.

**createDeltaPkg with build passthrough options:**

When templating runs inside `createDeltaPkg`, these flags are forwarded to the build path used by `build` / `buildTemplate` / `buildDefinitionBulk`:

| Option | Alias | Purpose |
| :-- | :-- | :-- |
| `--retrieve` | `-r` | Re-retrieve metadata before templating when applicable (see `build` / `buildTemplate` docs) |
| `--skipValidation` | `--sv` | Relax validation from error to warning where supported |
| `--purge` | — | Clear the relevant deploy output before building definitions |
| `--no-purge` | — | Skip confirmation and do not delete deploy output first |
| `--fix` | — | Apply automatic fixes where rules support it |
| `--shareAsset` | — | Retain asset sharing information during templating; see [asset sharing guidance](/Accenture/sfmc-devtools/wiki/08.-Metadata-specific-settings-&-options#asset-sharing) |

For example, `mcdev createDeltaPkg --range prod --shareAsset` keeps sharing information for the templating path. Review sharing permissions and template MID values for the target BUs; this flag is not a substitute for choosing the intended recipients.

> **Detailed background (Git-derived deltas):** `createDeltaPkg` compares Git endpoints to select changes, then calls the combined `build` path for relevant metadata. That path temporarily redirects templates to `.mcdev/template/`, renders definitions into the configured `directories.templateBuilds` destinations (normally `retrieve/` and `deploy/`), and removes the temporary template directory on normal completion. Cleanup is not guaranteed after every early exit or failure. Standalone `buildTemplate` still uses the configured template directory. Deployment is a separate operation, not part of `createDeltaPkg`.

**Git selection is not a historical content checkout.** The range selects changed paths from committed endpoints, but mcdev checks file existence, reads metadata and copies/builds content from the current filesystem. Staged or unstaged edits to selected components can therefore affect the package. Ensure the working tree contains the intended deployment snapshot, including companion files; a range does not reconstruct those files from its target commit.

**Interactive commit selection:**

This selects changed paths by comparing your latest commit with a previous commit. It does not select additional paths solely because they have staged/unstaged edits, but package content comes from the current filesystem as explained above. This approach is especially useful if you are in charge of the deployment and simply want to compare the latest commits to your main / release branch with the commit that was last deployed.

> **Important**: Make sure you are on the branch corresponding to the environment you want to deploy to, e.g. the main branch.

```bash
mcdev createDeltaPkg
```

**Manual commit selection:**

This is what you would do when you work on a feature branch and want to include the proposed changes for the target BUs already in the branch.

```bash
# Option 1 - RECOMMENDED
# compare based on what you last committed
# you just committed all your changes and want to create the deployment package for main/Production;
# Recommendation: run this before creating a pull request to include the changes in your PR.

mcdev createDeltaPkg --range main # resolves to main..HEAD
```

Alternatives:

```bash
# the same example with another branch name:
mcdev createDeltaPkg --range "release/sprint-14" # resolves to release/sprint-14..HEAD

# or even use a commit ID instead of a branch name
mcdev createDeltaPkg --range d21b4221  # resolves to d21b4221..HEAD


# Option 2 - full git range
mcdev createDeltaPkg --range main..develop
```

**Manual commit selection without templating:**

If you don't want to use templating, you may instead provide the optional `filter` parameter. If the `filter` option is used, then no markets/marketLists are used - and it does not use `buildTemplate` nor `buildDefinition` internally. Therefore, you should only expect changes in your deploy/ folder, not the template/ folder.
Instead, it creates a 1:1 copy of relevant files in the deploy folder. This is particularly useful for people that make a lot of changes with search & replace and then need to know which files have to be deployed.

```bash
mcdev createDeltaPkg --range d21b4221..HEAD --filter 'MyProject/BU1'
```

Range and multiple filters (without templating):

```bash
mcdev createDeltaPkg --range d21b4221..HEAD --filter 'MyProject/BU1,MyProject/BU3'
```

No Range and filter that includes metadata type (without templating):

```bash
mcdev createDeltaPkg --filter 'MyProject/BU1/asset/template'
```

> **Note to CLI experts:**
>
> In `--filter` copy mode, supplying a range avoids commit selection, and `--skipInteraction` (aliases `--yes`, `-y`) automatically removes the selected credential/BU deploy subdirectories before copying current files. This copy-mode cleanup does not consult `--no-purge`; do not use it as a cleanup opt-out here.
>
> ```bash
> mcdev createDeltaPkg --range main --filter 'MyProject/BU1' --yes
> ```
>
> In the templated path without `--filter`, combined `build` still asks about cleanup unless `--purge` or `--no-purge` is supplied, even with `--yes`. Omitting the range still opens commit selection. Review and approve the applicable cleanup before choosing unattended execution.

## Components that require pre- or post-deployment steps

### Generic: Deleted components

mcdev cdp (createDeltaPkg) generates a ready-to-copy mcdev delete command with everything it THINKS needs to be deleted. DO check that because renamed components might be in this list. Do NOT assume this list is always correct!
> 👈👉 Do this as a pre- or post-step.

### Generic: Changing the key (renamed components)

mcdev has no way of knowing that you changed a key and with it the filename. If you component is used by other metadata, the link might be broken if you simply delete + re-deploy this. Be VERY careful in this situation and ideally do the key-change as part of a hotfix during which you actively change the keys rather than follow the normal deployment process!
> 👈 Do this as a pre-step.

### DataExtensions

#### Changing Retention settings

This can be achieved via Contact Builder, but currently not via Email Studio nor via mcdev. 
> 👈👉 Do this as a pre- or post-step. Pre is faster.

#### Synchronized DataExtensions

You have to create/update them manually via UI, but the change does show up on your Parent BU alongside updates to changed attribute groups & attribute sets on the child BU. Therefore, to track these changes, make sure you have your team commit them to your git repository.
> 👈 Do this as a pre-step.

#### Shared DataExtensions

You can deploy them via mcdecv but be aware that they will only show in your Parent BU's folder. Making changes to them can affect your child BUs attribute groups and attribute sets. Actual sharing is handled via their folders and can only be done in the UI. It is recommended to have mcdev handle folder creation during deployment and then take care of sharing afterwards manually. Be aware that shared DE folders initially grant access to all BUs.
> 👉 Do this as a post-step.

### DataExtension fields

#### Renamed DataExtension fields

Similar to changing the key of things, this should be done as part of a hotfix. If you choose to deploy this through the automated pipeline, it will simply add a new field instead. Either change the field name in the UI or follow this guide to change a field name via mcdev: https://github.com/Accenture/sfmc-devtools/wiki/08.-Metadata-specific-settings-&-options#renaming-fields-of-a-data-extensions
> 👈 Do this as a pre-step.

#### Deleted DataExtension fields

As of now, mcdev will not automatically remove fields that are no longer in your deployment package. Instead it will simply not touch them. If you want fields deleted, you need to do so via UI or via mcdev delete MyProject/_ParentBU_ -m dataExtensionField:MyUserTable.MyFieldName
> 👈👉 Do this as a pre- or post-step. Pre is faster.

#### Adding a new Primary Key field

You cannot add a new primary key field to an existing table that has data. Therefore, if you that's what you need to do, export the data first, empty the DataExtension, run the update and then import the data again.
> 👈+👉 Do this as a pre- AND post-step.

#### Changing the field type

You cannot change the field type but you can delete and recreate a field with the same name. Therefore, if you that's what you need to do, export the data first, empty the DataExtension, run the update and then import the data again.
> 👈+👉 Do this as a pre- AND post-step.

### File Locations

It’s not supported by mcdev but required by import file activities
> 👈 Do this as a pre-step.

#### Domain Verifications / From Name Management

SAP / Registered Domain / Private Domain need to be set up manually via UI or else actual emails that can get created wont be automatically verified.
> 👈 Do this as a pre-step.

### Cloudpages (asset-webstudio)

mcdev does not create new `asset-webstudio` members: create them via the SFMC UI first, then retrieve them before updating their content or key. This applies to `webpage`, `webtemplate`, `cloudpages`, `landingpage`, `microsite`, `interactivecontent` and the JavaScript, CSS, JSON, RSS, text and XML code-resource members of this group, not just Cloudpages. A retrieved Cloudpage's content appears under `asset/webstudio` with a UUID key, `assetType.name: "webpage"` and the page's name.
> 👈 Do this as a pre-step.

To enable easy deployments of changes to the cloudpage, it is recommended to keep your actual cloudpage code in a code snippet and then reference that code snippet in the cloudpage. This way, you can easily update the code snippet and the cloudpage will automatically reflect the changes without a need to re-publish it:


**Your Cloudpage code:**

```html
%%=ContentBlockByKey("myCloudpage_codesnippet")=%%
```

**Your Cloudpage code snippet (key:"myCloudpage_codesnippet"):**

```html
<!--insert whatever HTML, Ampscript/SSJS or other code you need here-->
```

This way, whenever you want to update this cloudpage, simply update the code snippet ("myCloudpage_codesnippet" in the above sample) and the cloudpage will automatically reflect the changes.
