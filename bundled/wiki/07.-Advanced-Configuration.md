The tool's configuration can be changed in the file `.mcdevrc.json` located in the root of your project folder.

It contains [Market Configuration](#market-configuration) (`markets: { ... }`), [Market List Configuration](#market-list-configuration) (`marketList: { ... }`) the list of usable Business Units per credentials, `directories`, as well as other `options`.

You will also find the configuration for what metadata shall be retrieved here in `metaDataTypes.retrieve: [ ... ]`.

You will also find a secondary file named `.mcdev-auth.json` containing your credentials. **Do not commit this to your repository!** You should only commit `.mcdevrc.json` as this file contains project-wide settings that do not compromise security.

## v10 asset selectors and migration scope

**v10:** use `asset-email` instead of `asset-message`. Historical `jsonmessage` assets belong to `asset-mobile`; page/code-resource families use `asset-webstudio`. `jsonmessagetemplate` remains in `asset-template`, and `asset-asset` remains valid for its current members. Review `metaDataTypes.retrieve`, `metaDataTypes.createDeltaPkg`, subtype filters and custom CI/path filters: old broad groups may split across several current groups. Obsolete `asset-message`, `asset-cloudpage` and `asset-coderesource` have no operational aliases.

`mcdev upgrade` may replace subtype selections with current defaults through its normal configuration update. Review and reapply custom scope, then commit. It does not move files. `mcdev migrate cred/bu` operates only under the configured `directories.retrieve` for one exact configured BU, and `mcdev migrate cred/*` covers every BU of one credential in a single run (per-BU reporting, with a conflict in one BU not stopping the others); deploy/template trees need manual migration. Bare `mcdev migrate` opens interactive BU selection. Only exact `cred/*` for a configured credential expands to all its BUs; other unresolved selectors, including bare `*` and `unknownCredential/*`, use the existing interactive credential/BU selection (`--skipInteraction` logs an error instead). Selectors with extra slash components or empty components are rejected without selection. See [Migrating to v10](/Accenture/sfmc-devtools/wiki/03.a-~-Migrating-to-v10) for complete mappings.

For templated delta packages, `options.deployment.branchSourceTargetMapping` is keyed by the **exact supplied comparison range string**, not necessarily the current branch. When no entry matches, `sourceTargetMapping` is the fallback. Its source market list selects the same source BU path on both Git endpoints; its target market list selects output destinations. See [Git-based deployments](/Accenture/sfmc-devtools/wiki/06.d-~-Git-based-deployments-and-CICD) before changing range spellings or preparing environment branches.

### Validation rules

You can define validation rules for `retrieve`, `buildDefinition` and `deploy`. 
The following rules exist out of the box:

- noGuidKeys: test for metadata that has a GUID / UUID as key.
- noRootFolder: test if metadata that does exist in a folder resides in the root for that particular type or in a subfolder.
- noAmpscriptHtmlTag: alerts you if `<script runat="server" language="ampscript"> ... </script>` was used to frame AMPscript instead of `%%[ ... ]%%`

Possible rule settings are:

- not set, which implicitly turns off the rule
- "off" explicitly turns off the rule
- "warn" shows a log message of type warning
- "error" shows a log message of type error AND blocks further execution
  - for `retrieve` that prevents download
  - for `buildDefintion` (and `build`) that prevents the creation of the corresponding file in the deploy folder
  - for `deploy` this will prevent deployment.
- "fix" can either lead to skipping the component or to updating parts of the metadata (JSON) - that depends on the rule's algorithm. If fixing means skipping then the outcome is the same as with "error", except that no error code is returned by mcdev which can be relevant if you execute mcdev as part of a CI/CD pipeline where an error code signals a problem.
- "fixR" (retrieve only) is like "fix" but only applies during retrieve operations

Adding `--skipValidation` (or `--sv`) to retrieve / deploy / build / buildDefinition / buildDefinitionBulk does not turn off validation. Enabled checks still run, but ordinary failed checks are reported as warnings instead of blocking errors, and validation fixes are suppressed. This does not suppress every exception or other command failure.

For retrieve operations with `--fix` flag, rules configured with "fix" or "fixR" will attempt to automatically correct issues when possible.

### Custom Validation rules - .mcdev-validation.js

Optionally one can create a file named `.mcdev-validations.js` in the root of your project to specify your own validation rules. That gives you full flexibility to test for whatever guidelines you might have as you can literally parse the JSON of the metadata yourself.

One example that depends on BU names and hence is not part of the standard set could look like this:

```js
'use strict';

const buSuffixMap = {
    _ParentBU_: '',
    DEV: '_DEV',
    QA: '_QA',
    PROD: '',
};

/**
 *
 * @param {any} definition type defintiion
 * @param {any} item metadata json
 * @param {string} targetDir where the metadata is stored ("deploy/cred/bu")
 * @param {any} Util helper methods
 * @returns {Promise.<any>} validation rule
 */
export function validation(definition, item, targetDir, Util) {
    const bu = targetDir.includes('/') ? targetDir.split('/').pop() : targetDir.split('\\').pop();
    const suffix = buSuffixMap[bu];

    if (suffix === undefined) {
        Util.logger.error(
            `BU '${bu}' not defined for keySuffix validation in .mcdev-validations.js`
        );
    }
    return {
        keySuffix: {
            failedMsg: 'Key Suffix expected but not found: ' + suffix,
            /**
             * @returns {boolean} true=test passed
             */
            passed: function () {
                // exclude non-relevant items
                const relevantTypes = ['asset', 'dataExtension'];
                if (!relevantTypes.includes(definition.type)) {
                    return true;
                }
                if (
                    definition.type === 'dataExtension' &&
                    item.r__folder_ContentType !== 'shared_dataextension'
                ) {
                    // only shared DEs need a suffix
                    return true;
                }

                // actual test
                const key = item[definition.keyField] + '';
                if (key) {
                    return key.endsWith(suffix);
                } else {
                    Util.logger.debug('validation-keySuffix: key not found');
                    return true;
                }
            },
        },
    };
}
```

To control how a custom rule is applied, simply add its name (in the above example, `keySuffix`) to options.validation like you would for the default rules. Because **custom rules** are configured in the same way as default rules, you can also use the same override logic for them

```json
    "validation": {
            "retrieve": {
                "keySuffix": "warn",
                "noGuidKeys": "warn",
                "noRootFolder": "warn",
            },
            "buildDefinition": {
                "keySuffix": "warn",
                "noGuidKeys": "warn",
                "noRootFolder": "warn",
                "overrides": [
                    {
                        "type": [
                            "asset"
                        ],
                        "options": {
                            "keySuffix": "error",
                        }
                    }
                ]
            },
            "deploy": {
                "keySuffix": "error",
                "noGuidKeys": "error",
                "noRootFolder": "error",
            }
    },
```

## Market Configuration

You will want to set up configs for variable parts that change between Business Units. We advise starting this _after_ you've first run the `buildTemplate` or `build` command. This might sound counterintuitive, but when you review what was copied into your template folder you will likely spot these variable parts the fastest and can then start setting up your market config. Please consider this an iterative process, as you will likely run `bt`/`build` followed by additional config updates until you get it right.

We advise clustering your logical approach into variable things on the **instance parent** (=`_ParentBU_` in Accenture SFMC DevTools), the **environment parent** (under which you cluster your child Business Units for DEV, QA, and PROD respectively), and **child Business Units**. Ideally, the instance parent is only used to deploy _Shared Data Extensions_, the environment parent is used for integrations with external services and to separate incoming data via Automations into the respective _Shared Data Extensions_. The child Business Units are then reserved for everything that is run on a market-by-market basis.

_Note:_ We do see it often that instance parent and environment parent are the same. This depends on your client's setup since Business Units are not for free, and clients sometimes decide to save the extra money. Sometimes, you even end up with only one BU for DEV activities, no QA environment - and share the instance parent between DEV and production... This is not the recommended approach for multiple reasons, including security, but it is the reality in some of our projects.

### Regex market variables

Existing scalar market variables remain compatible: strings, numbers, and booleans use the existing literal replacement behavior. You can mix scalar variables and regex objects in the same market. The special handling of `description` and the existing fallback behavior remain unchanged.

For more selective matches, configure a variable as an object:

- `search`: a JavaScript regular expression source, without `/` delimiters or flags. It is applied globally when building a template (`buildTemplate` / `bt`), replacing every match.
- `replace`: a literal string, number, or boolean used when building a definition (`buildDefinition` / `bd`). It is not a JavaScript capture-group replacement expression.
- `template` (optional): a native JavaScript replacement string used when building the template. Capture references such as `$1` and `$2` preserve parts of the match. If omitted, it defaults to `{{{key}}}`, where `key` is the market variable's name.

#### Match an exact quoted value

The following `.mcdevrc.json` example matches the complete quoted value `"Dynamic"` rather than every occurrence of `Dynamic`:

```json
{
    "markets": {
        "source": {
            "senderProfile": {
                "search": "(\")Dynamic(\")",
                "replace": "Dynamic",
                "template": "$1{{{senderProfile}}}$2"
            }
        },
        "target": {
            "senderProfile": {
                "search": "(\")Transactional(\")",
                "replace": "Transactional",
                "template": "$1{{{senderProfile}}}$2"
            }
        }
    }
}
```

The first and second capture groups contain the surrounding quotes. The replacement `$1{{{senderProfile}}}$2` therefore produces `"{{{senderProfile}}}"`, keeping the JSON template valid. Values such as `"Dynamic Sender Profile"` and `"OrderConfirmationDynamic_DEV"` remain unchanged. Building with the source market restores `"Dynamic"`; building with the target market produces `"Transactional"`. The target's `search` lets that value be templated again using the same variable.

#### Match a sender profile field prefix

To replace only the local-part prefix in `FromAddress`, while leaving occurrences in other fields alone, use this `.mcdevrc.json` example:

```json
{
    "markets": {
        "source": {
            "regex": {
                "search": "(\"FromAddress\":\\s*\")joern",
                "replace": "joern",
                "template": "$1{{{regex}}}"
            }
        },
        "target": {
            "regex": {
                "search": "(\"FromAddress\":\\s*\")thuy",
                "replace": "thuy",
                "template": "$1{{{regex}}}"
            }
        }
    }
}
```

For example, `"FromAddress":"joern@example.com"` becomes `"FromAddress":"{{{regex}}}@example.com"`. The capture group preserves the field name, colon, optional whitespace, and opening quote; the domain and closing quote are outside the match and stay intact. Building for the source restores `joern@example.com`; building for the target produces `thuy@example.com`.

**Important: match the text mcdev actually searches.** JSON metadata is searched as compact `JSON.stringify` output, not the pretty-printed file on disk. There is no space after a colon in that serialized output, so a pattern containing the literal space in `"FromAddress": "joern` will not match it. The JSON regex source `"(\"FromAddress\":\\s*\")joern"` allows zero whitespace as well as whitespace when present. Write `\\s*` in JSON so the parsed regular expression receives `\s*`.

Embedded newlines in JSON string values are escaped in the serialized metadata; they are not actual line breaks for a whitespace regex to match. Extracted code files, on the other hand, retain actual whitespace and newlines, so `\s*` can match those characters there.

These are text-only replacements. A numeric or boolean `replace` value renders as text; native JSON type-preserving templating of number or boolean fields is out of scope. Keep the surrounding syntax valid, including quotes and any required escaping in JSON strings.

## Market List Configuration

Market Lists are very powerful and you will quickly notice how much time they can save you during your deployment preparation.
Let's first look at an example list config:

```json
// this is a market-list-config based on the example market-config listed above!
"markets": {...},
"marketList": {
    "deployment-source": {
        "description": "Define one 1:1 BU-Market combo here to as source for automated creation of deployment packages; you can create more than one source market list",
        "MySandbox/DEV-NL": "DEV-NL"
    },
    "deployment-target": {
        "description": "Define n BU-Market combo here to as target for automated creation of deployment packages; you can create more than one target market list and they can be as complex as you like",
        "MySandbox/QA-DE": "QA-DE",
        "MyProduction/PROD-DE": "PROD-DE",
        "MyProduction/PROD-NL": "PROD-NL"
    }
}
```

The above can be used together with `createDeltaPkg` command.

Way more complex example:

```json
// this is a market-list-config based on the example market-config listed above!
"markets": {...},
"marketList": {
    "Parent-shared": {
        "description": "used to deploy shared data extensions",
        "MySandbox/_ParentBU_": ["QA-DE", "QA-GULF"],
        "MyProduction/_ParentBU_": ["PROD-AT", "PROD-CH", "PROD-DE", "PROD-GULF", "PROD-NL"]
    },
    "Parent-medium": {
        "description": "if you use the instance's parent BU also for imports",
        "MySandbox/_ParentBU_": "QA-Parent",
        "MyProduction/_ParentBU_": "PROD-Parent"
    },
    "Parent-large": {
        "description": "very large projects often decide against using the instance parent to get more order into the chaos and define their own 'parents' instead",
        "MySandbox/QA-_Parent_": "QA-Parent",
        "MyProduction/ProjectX-_Parent_": "PROD-Parent"
    },
    "Parent-medium-multi": {
        "description": "equal to Parent-shared"
    },
    "Parent-large-multi": {
        "description": "use to deploy market-adapted queries to your parent BUs",
        "MySandbox/QA-_Parent_": ["QA-DE", "QA-GULF"],
        "MyProduction/ProjectX-_Parent_": [
            "PROD-AT",
            "PROD-CH",
            "PROD-DE",
            "PROD-GULF",
            "PROD-NL"
        ]
    },
    "Children": {
        "description": "use this to deploy to your market BUs",
        "MySandbox/QA-DE": "QA-DE",
        "MySandbox/QA-GULF": "QA-GULF",
        "MyProduction/PROD-Child_AT": "PROD-AT",
        "MyProduction/PROD-Child_CH": "PROD-CH",
        "MyProduction/PROD-Child_DE": "PROD-DE",
        "MyProduction/PROD-Child_GULF": "PROD-GULF",
        "MyProduction/PROD-Child_NL": "PROD-NL"
    }

```

First off, we don't see DEV in here. If you have more than one market in DEV then this might deviate but in general, you don't want to bulk-deploy to DEV as this is your single source of truth.
Apart from that, we can see 4 types of lists here:

1. `Parent-shared` (_instance parent_): This would be used to deploy the Shared Data Extensions to the instance parent. The child-configs are listed in an array to ensure we end up with one file per child in our parent BU folder.
2. `Parent-medium`/`Parent-large` (medium:_instance parent_; large:_environment parent_): A 1:1 config that handles automations and the part of your solution that only runs on the parent.
3. `Parent-medium-multi`/`Parent-large-multi` (medium:_instance parent_; large:_environment parent_): Any scripts, queries, automations that are executed on the parent but require one per child (e.g. query to fill country-specific Shared Data Extensions)
4. `Children` (_child BUs_): everything that is needed on the market-specific Business Units.

## CLI Options

These flags apply to **any** `mcdev` subcommand unless noted otherwise.

### --verbose

Increases detail in CLI output.

### --debug

Enables developer-oriented behavior and edge-case features where the tool supports them.

### --silent

Limits CLI output to errors only.

### --skipInteraction (aliases: `--yes`, `-y`)

Skips prompts where supported, using defaults or command-specific `--y.*` answers (for example during `init` or `fixKeys`). It is not a universal noninteractive switch. Supply valid explicit credential/BU selectors: omitted selectors can still prompt, while unknown selectors can fail. Combined `build` still asks about deploy-output cleanup unless `--purge` or `--no-purge` is supplied; `createDeltaPkg` without a range still asks for a base commit. See the relevant command sections and [unattended setup prerequisites](/Accenture/sfmc-devtools/wiki/06.a-~-Admin-Commands#init).

### --api=[log|cli]

The normal `logs/<timestamp>.log` already records debug-level messages. `--api log` (or `--api=log`) additionally records API requests and responses there; `--api cli` prints them directly in the terminal. Diagnose the relevant normal log first and use API logging only if more detail is needed. Adding the flag executes the command again: reconcile partial effects and approve repeated overwrites or remote changes before rerunning it. Logs can include sensitive command arguments and API bodies despite limited token masking; do not share raw logs or authentication files. See [Troubleshooting](/Accenture/sfmc-devtools/wiki/04.-Troubleshooting#diagnosing-a-failed-command).

Examples:
```batch
mcdev retrieve --api=log
mcdev deploy --api=cli
```

### --noLogFile

Disables file logging: neither the normal logfile nor the optional error-only companion is created. Console logging remains enabled.

Examples:
```batch
mcdev retrieve --noLogFile
mcdev deploy --noLogFile
```

### --noLogColors

Optionally, you can disable colors in CLI output. This is useful if you integrate mcdev into systems that cannot display color codes.

Examples:
```batch
mcdev retrieve --noLogColors
mcdev deploy --noLogColors
```

### --errorLog

Optionally, mcdev can create a second log file ending on `-errors.log` that only contains log entries of type "error" for quick parsing and potential visualization in a GUI. This companion is created on demand when an error is logged. It does not contain the normal logfile's debug details; use the invocation's normal `.log` first for diagnosis.

Note: This will not work in combination with `--noLogFile`

Examples:
```batch
mcdev retrieve --errorLog
mcdev deploy --errorLog
```
